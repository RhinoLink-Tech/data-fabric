# v2.0.0 Core Release Candidate Review

**Status:** Candidate preparation only. No v2.0.0 tag or stable GitHub Release has been created. Publication remains blocked by the unresolved P0 credential rotation in #12 and written release-risk decisions for the open P1 security items #218 and #220.

## Version and scope decision

The next core release should target **v2.0.0**. Since v1.2.0, the gateway changed authentication requirements, data-source ownership, and name uniqueness in ways that require deployment changes. A patch or minor version would understate these compatibility changes.

The latest published stable release is v1.2.0. This candidate verifies upgrades from v1.2.0 only; earlier versions need a separate rehearsal. The security-maintenance candidate discussed in #206 is separate and is not a published v1.2.1 release.

The exact candidate commit, downloadable source archive checksum, and final validation links are recorded in [issue #211](https://github.com/RhinoLink-Tech/data-fabric/issues/211) after the final documentation commit and checks.

## Compatibility changes users must plan for

- **Configuration file:** configs/config.yaml is no longer tracked. Back it up securely before upgrading and recreate local configuration from configs/config.yaml.example; the example contains placeholders.
- **JWT secret:** HTTP startup requires a non-placeholder secret of at least 32 bytes. There is no built-in default. SECURITY_JWT_SECRET is canonical; JWT_SECRET remains a compatibility alias.
- **Fetch authentication:** Both initial and continuation /api/v1/fetch requests require a Bearer token even when security.enable_auth is false. Release mode also requires security.enable_auth: true.
- **Data-source ownership:** New rows are assigned to the authenticated caller and tenant. Legacy rows without ownership metadata are visible only to administrators; ownership is not guessed or silently assigned.
- **Name uniqueness:** Names are unique per tenant instead of globally. The migration replaces the old global uniqueness index.
- **Credential encryption:** The HTTP and MCP servers require a persistent credential keyring. Keep existing key material across restarts and migration; losing it makes stored credentials unreadable.
- **Toolchain:** The source requires Go 1.26.1.

Detailed steps are in [Upgrading from v1.2.0](../upgrading-v1.2.0.md).
