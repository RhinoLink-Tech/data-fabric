# v1.2.1 Security Maintenance Candidate

This candidate is based on the published v1.2.0 source tag (5b927f8723406b36df206b7b3e7fe6921f72e84e). It is limited to a security maintenance line for users upgrading from v1.2.0.

## Included changes

- Remove the tracked local configs/config.yaml; provide configs/config.yaml.example with no secrets.
- Require a 32-byte, non-placeholder JWT secret on HTTP startup and require Bearer authentication on both /api/v1/fetch routes, regardless of security.enable_auth.
- Encrypt data-source passwords and secret-valued additionalProps at rest with an AES-256-GCM keyring.
- Migrate existing plaintext data-source credentials in a database transaction before serving requests. Startup fails closed if migration or decryption fails.
- Redact credentials from data-source API responses.

## Upgrade notes

1. Back up the metadata database and any local configs/config.yaml before upgrading.
2. Set DATABASE_USERNAME, DATABASE_PASSWORD, and a newly generated JWT_SECRET (at least 32 bytes).
3. Set DATA_FABRIC_CREDENTIAL_ACTIVE_KEY_ID and DATA_FABRIC_CREDENTIAL_KEYS before first startup. The latter is a JSON object mapping key IDs to base64-encoded 32-byte keys. Keep these keys in a secret manager and back them up separately from the database.
4. On first startup, the service encrypts existing plaintext data-source passwords and sensitive additional properties in one transaction. If the transaction fails, the service refuses to start; restore the database backup or correct the key configuration before retrying.
5. All clients calling POST /api/v1/fetch or the continuation GET /api/v1/fetch/{query_id}/{slug}/{token} must send a valid Bearer token. security.enable_auth controls data-source management routes only.
6. The candidate supports upgrades from v1.2.0 only. No released container image or binary is produced; the current distribution remains the GitHub source archive.

## Known limitations

- Issue #12's operational rotation of credentials that appeared in repository history remains separate. Removing the file from this candidate does not erase old Git history or rotate external database/JWT credentials. Treat those values as exposed and rotate them in the deployment environment.
- This maintenance candidate does not add per-user/tenant data-source authorization or database-session read-only enforcement. Use least-privilege database accounts and keep existing SQL validation enabled.
- A disposable MySQL 8.0 run verified clean installation and migration of a synthetic v1.2.0-shaped metadata table, including credential read/decryption and API redaction. SQLite repository tests also verify migration rollback on a missing key. Issue #209 covers broader MySQL baseline and recovery cases.
