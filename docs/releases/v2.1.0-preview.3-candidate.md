# Data Fabric v2.1.0-preview.3 candidate and risk record

**Channel:** developer Preview. [中文](v2.1.0-preview.3-candidate-zh.md) · The latest stable release remains v2.0.0. This document describes the proposed evaluation scope and the evidence required before publication. It is not a tag, image, GitHub Release, marketplace update, or support promise. The matching release record must name the final source SHA, image digest, source-archive checksum, and actual acceptance results.

**Preparation baseline:** master `b5cdceb8dcdeafda33f16aca84de15f421607ca5` on 2026-11-25. This record changes source files when it is merged, so no test result cited for this baseline is artifact evidence for the eventual tag. Freeze and retest the exact tagged commit.

## Supported evaluation profile

One self-hosted `linux/amd64` host using the documented Compose profile, MySQL 8.4 metadata and synthetic MySQL sample data, REST management, and remote MCP with a correctly configured external OIDC issuer and trusted TLS. The published image must bundle the pinned SQL translation runtime and license materials. Select other data sources only within the operations and verification evidence recorded in the [support catalog](../data-source-support.md).

This is an evaluation release, not a production-readiness, high-availability, automatic-failover, support-window, performance-SLA, universal SQL, ELT, or cross-connector compatibility promise. The tested single-host profile does not establish cluster-wide query budgets or cursor failover. Deployment time and resource use depend on the host and workload.

The public WorkBuddy service, self-service tenant provisioning, arbitrary-client automatic OAuth onboarding, and marketplace lifecycle are outside the supported profile. Browser-based source onboarding and update flows are default-off candidates that need their own identity, network, driver, and client acceptance. A published image does not prove those flows work in WorkBuddy.

## Candidate user-visible changes

- **Read-only agent data access:** MCP source discovery and authorized table inspection are paginated and caller-relative. Where metadata supports it, table results include an authorized schema-qualified identity so same-named tables can be distinguished.
- **Bounded queries:** initial MCP pages default to 100 rows, explicit page sizes can reach 10,000, and continuations retain the effective limit. Explicit no-count results are limited to MySQL, MariaDB, PostgreSQL, and Trino; unknown totals are `null`, while exact count remains the default.
- **SQL conversion:** the repository Skill and REST/MCP conversion capability discover advertised dialects, normalize documented aliases, validate same-dialect input, and translate without executing the SQL. Conversion is not a guarantee that arbitrary vendor SQL is semantically portable.
- **Safer source operations:** source creation and update use connector-specific validation; an authorized editor can test retained server-side credentials without receiving them. Expired or unavailable browser-onboarding flows instruct the user to restart from the MCP client without storing a password in browser storage.
- **Explicit support boundaries:** GBase 8s/8t configurations now fail rather than silently using an unverified adapter, and DaMeng is unavailable if its native driver is absent. These are safety disclosures, not newly supported sources.

## Artifact and acceptance gates

1. Merge this candidate record, freeze the exact master commit, and require successful push CI for that SHA, including affected-contract selection, unit/build checks, reference PostgreSQL/MySQL/MariaDB contracts, and public REST/MCP acceptance.
2. Run the isolated encrypted backup and fresh-volume recovery workflow for the exact frozen SHA. It is source-candidate evidence only; retain a separate rehearsal for the older published image.
3. Recheck the source matrix, release notes, known limits, and the written risk decisions. Move the reviewed Unreleased entries into the selected dated version only when the version/tag decision is made.
4. Confirm the version and source-SHA image tags are unused. Create an annotated `v2.1.0-preview.3` tag on the exact reviewed master commit. The tag workflow must publish a `linux/amd64` image with SBOM and provenance.
5. Record the public immutable `tag@sha256` reference, source revision, and platform. Dispatch the published-image acceptance workflow against that exact digest; documented no-Go installation, embedded UI, standalone REST/MCP, and two-replica checks must pass.
6. Create a source archive from the tag with `LICENSE`, `NOTICE`, and `THIRD_PARTY_NOTICES.md`; generate a basename checksum, upload both to a draft GitHub Release, and verify the downloaded pair in a new directory. Publish only after the release record accurately reflects the result and limits.
