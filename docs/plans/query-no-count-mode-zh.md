# 显式不计总数查询模式（设计）

[English](query-no-count-mode.md) · [Issue #450](https://github.com/RhinoLink-Tech/data-fabric/issues/450) · [当前结果契约](../query-result-semantics-zh.md)

**本文是设计，功能尚未实现或发布。** 现有 REST/MCP 的精确总数行为保持不变。

有些 AI 查询只需要首批预览或逐页读取全部结果，不需要先知道精确总数。当前分页遇到满页时会额外计数；流式路径也会在返回第一批前计数。计划让用户显式选择 `count_mode: "none"`，不执行辅助计数，并用 `totalCount: null` 表示未知、用 `hasMore` 和 `nextUri` 表示是否还有后续结果。未指定时保留现有精确计数；需要精确总数的客户端不受影响。

举例：首批可返回 `{"countMode":"none","totalCount":null,"hasMore":true,"entries":[[1],[2]],"nextUri":"..."}`；最后一批的 `hasMore` 为 `false` 且没有 `nextUri`，总数仍为 `null`。客户端应使用最新的查询 ID、slug 和令牌继续获取，不得把未知总数当作零，也不能把 SQL 自身 `LIMIT` 之外的数据视为已经取回。跨页并发修改和会话失效仍遵循现有边界。

在本机 2,000 行合成 SQLite 样本中，精确计数首批执行 2 条源 SQL，不计数的实验原型执行 1 条；取完全量分别为 21 条和 20 条。该原型只用于测量，并非已提供的接口；它不代表所有数据源、网络环境或生产性能。英文设计记录了复现命令、时间和分配量，以及参数、授权、预算、重放、失效和真实数据库验收要求。

实现前需要分别验证分页、流式游标和原生 API 的续页能力；无法证明完整性的来源应明确返回不支持，不能悄悄回退为计数或给出错误总数。功能实现及真实客户端验证完成前，不更新 WorkBuddy 平台能力声明。
